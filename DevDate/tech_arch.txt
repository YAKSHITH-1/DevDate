TECHNICAL ARCHITECTURE PLAN Project Collaboration & Skill-Matching Platform React Native (Expo) + Node.js + Express + MongoDB + Socket.io Document purpose Implementation blueprint for the MVP architecture and its production-ready extension path. Primary constraint 10-day college project; architecture must stay simple, explainable, testable, and deployable. Architecture style Modular monolith with a separate real-time transport path, not microservices. Primary clients React Native mobile app using Expo. Backend Node.js + Express.js REST API; Socket.io for chat events. Database MongoDB with Mongoose ODM and targeted indexes. Third-party integrations No required external business API for MVP; optional cloud image storage and push notifications only if time permits. 1. Architecture Goals Keep the entire MVP understandable to a student team and easy to defend in a viva. Centralize business rules in the backend so matching, project membership, and chat permissions cannot be bypassed by the client. Use a single deployable Node/Express application with clear modules before considering service decomposition. Support REST for ordinary CRUD/workflow operations and Socket.io only where near-real-time behavior materially improves the experience. Design indexes, validation, and uniqueness constraints up front to avoid avoidable data corruption and slow feed queries. Leave explicit extension points for notifications, image storage, analytics, and stronger recommendation logic without making them MVP dependencies. 2. Matching Engine Architecture Inputs   project.requiredSkills   project.requiredRoles   project.category / interests   user.skills   user.interests   user.role               ┌───────────────────┐               │ Skill Match (50%) │               └─────────┬─────────┘                         │               ┌─────────▼─────────┐               │Interest Match 30% │               └─────────┬─────────┘                         │               ┌─────────▼─────────┐               │ Role Match (20%)  │               └─────────┬─────────┘                         ▼              compatibilityScore 0..100 Skill score = matched required skills / required skills × 100. If no required skills exist, define the skill component as 0 rather than inventing a score. Interest score = overlapping project interests/category and user interests / project interest target set × 100. For the MVP, category can be treated as a single interest token when projects have one category. Role score = 100 when user.role is one of project.requiredRoles, otherwise 0. When a project specifies no required role, role component is 0. Final score = 0.50 × skill + 0.30 × interest + 0.20 × role. Round to nearest whole number for display. Compute score on feed retrieval or during response assembly; do not persist compatibility in the MVP unless performance profiling proves it necessary. Feed eligibility must exclude the project owner, full projects, the user's previously swiped projects, and closed/archived projects. 10. Swipe / Match State Machine User -> project    │    ├── PASS ───────────────► Swipe(action=pass) ──► no match    │    └── INTERESTED ─────────► Swipe(action=interested)                                   │                                   ▼                          Match(status=pending)                                   │                     owner accepts / rejects                          │             │                          ▼             ▼               Match(accepted)   Match(rejected)                          │                          ▼                   chat authorized Record the swipe before returning success so the feed cannot immediately re-present the same card. Create a pending Match only for interested actions; passes require only Swipe persistence. Acceptance must re-check project capacity atomically before changing Match to accepted and adding the user to Project.members. Rejection updates the existing pending request rather than creating another document. Accepted matches enable chat; rejected or pending users cannot send project messages. 11. Chat Architecture React Native    │ socket.io-client    ▼ Socket handshake with JWT    │    ▼ Server socket auth middleware    │    ▼ Join room: project:<projectId>    │    ├── send_message {projectId, text}    │       │    │       ├── authorize matched member    │       ├── validate length / content    │       ├── persist Message    │       └── emit new_message to room    │    └── disconnect / reconnect handled by client The server must never trust a projectId supplied by the client; membership is verified from Match/Project state. Persist the message before broadcasting so a successful UI send corresponds to durable state. Use message IDs generated by MongoDB/ObjectId to support deduplication on retries. For the MVP, typing indicators, read receipts, message editing, reactions, attachments, and presence are excluded. Rest remains available for history pagination so reconnecting clients do not depend on websocket event replay. 12. Trending Architecture MVP ranking uses a simple score based on number of interests, number of accepted matches, and recent activity. A deterministic implementation is recommended: trendingScore = interestedCount + acceptedMatchCount + recencyBoost. Recency boost can be a small bounded value such as max(0, 7 - ageInDays), preventing one old project from dominating forever. Counts may be computed by aggregation for MVP. Add denormalized counters only when profiling shows the aggregation is a bottleneck. Cache is optional; do not introduce Redis solely for trending in a 10-day build. 13. Authentication & Security Architecture Area Implementation Passwords Hash with bcrypt/argon2; never store plaintext. JWT Short-lived access token; sign with environment secret; validate issuer/audience if configured. Authorization Middleware extracts user identity; service layer enforces ownership and match permissions. Input validation Schema validation on every POST/PATCH route; trim strings; enforce max lengths. Rate limiting Apply to login, register, swipe, and message-send endpoints/events. CORS Allow only configured mobile/web origins where applicable; do not use wildcard in production APIs with credentials. Secrets Environment variables; never commit .env files. Logging Structured logs without passwords, tokens, or message content where avoidable. Abuse controls Basic block/report extension point; for MVP implement defensive validation and rate limiting. Database access Use least-privileged MongoDB credentials and TLS when hosted externally. 14. Availability, Reliability & Failure Handling Failure Expected behavior MongoDB unavailable API returns 503 for data-dependent operations; client shows retry state. Socket disconnect Client marks chat offline/reconnecting; queued sends are not silently considered delivered. Duplicate swipe Unique index prevents duplicates; return idempotent success or 409 according to endpoint contract. Concurrent accept at capacity Transaction/session or conditional update prevents exceeding teamSize. Expired/invalid JWT Return 401; client clears auth and routes to login. Project deleted/archived Exclude from discovery and block new interests. Message persistence failure Do not emit success event; client can retry using message intent/idempotency token if implemented. Network timeout Client retries safe GET requests; mutations should avoid blind retries without idempotency protection. 17. Observability & Diagnostics Log request method, route, status, latency, request ID, and authenticated user ID where appropriate. Log critical domain transitions: project creation, interest, accept/reject, match creation, and socket connect/disconnect. Never log passwords, JWTs, or full private message content. Add a /health endpoint that checks process health and a lightweight database ping. For the MVP, console + structured JSON logs are sufficient; a hosted error tracker can be added without changing domain architecture. 18. Scalability Path Beyond MVP If feed aggregation becomes slow, introduce precomputed compatibility candidates or a search index rather than immediately creating microservices. If websocket traffic exceeds one instance, add Redis as the Socket.io adapter and use multiple stateless API/socket nodes. If notifications become substantial, introduce a queue/worker process for push/email jobs. If project images become numerous, move all binary assets to object storage + CDN and store only URLs in MongoDB. If recommendation quality becomes a product differentiator, replace the deterministic matcher with a dedicated recommendation service while preserving the same compatibility API contract. 24. Architectural Non-Goals for the 10-Day MVP No microservices. No Redis requirement. No GraphQL. No Kubernetes. No AI recommendation service. No OAuth. No GitHub API integration. No video calling. No complex notification pipeline. No full project-management suite. No payments. No social graph/followers/stories/comments/likes. 25. Final Architecture Recommendation Build a modular monolith: React Native/Expo -> Express/Node -> MongoDB. Use Socket.io as a narrow, authenticated real-time layer for project chat; persist all messages in MongoDB. Keep matching deterministic and backend-owned: 50% skills, 30% interests, 20% role. Use MongoDB uniqueness constraints and conditional updates to protect workflow integrity. Make optional third-party services additive rather than required: cloud image storage and push notifications can be added without changing core business logic. Optimize for demo reliability first; only introduce Redis, queues, search, or microservices when there is measured need.
